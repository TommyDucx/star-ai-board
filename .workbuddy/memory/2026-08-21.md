## 公网 HTTPS 下两个页面都没棋盘（**真根因，重大教训**）

- **根因**：chess.js 和 go.js 的 `connect()` 用 `new WebSocket(\`ws://${location.host}\`)`（明文 WebSocket），公网 trycloudflare.com 是 HTTPS 页面 → 浏览器阻止 ws:// 连接并抛 `SecurityError: Failed to construct 'WebSocket': An insecure WebSocket connection may not be initiated from a page loaded over HTTPS` → 异常中断整个 IIFE → 后面的 `loadEngines()`/`initBoard()` 不执行 → 棋盘不渲染。
- **为什么之前调试没发现**：puppeteer 真实浏览器（`puppeteer-core` + 系统 Chrome）才能抓到这个错误。Headless Chrome 命令行 `--dump-dom` 在沙箱下不稳定（exit 127/137），`--screenshot` 有缓存误导；puppeteer 是最可靠的复现用户实际浏览器的方式。
- **修复**：`ws://${location.host}` → `${location.protocol === "https:" ? "wss:" : "ws:"}//${location.host}`；connect() 包 try/catch 防止 ws 异常阻断棋盘初始化。chess.js 和 go.js 同样修复。
- **附加修复**：server.js 静态文件响应加 `Cache-Control: no-cache, no-store, must-revalidate`（之前没设，浏览器对静态资源做启发式缓存，导致用户浏览器缓存了旧 JS/CSS）。HTML/CSS/JS 全部资源加版本号（chess.html/css/js → ?v=25，go.html/css/js → ?v=4），每次改动递增强制刷新。
- **教训（极重要）**：
  1. WebSocket URL 必须协议自适应（HTTP→ws、HTTPS→wss），否则 HTTPS 页面会因 ws:// 被拦截。
  2. 调试公网问题时必须用 puppeteer（真实浏览器），headless Chrome 命令行在沙箱下不可靠。
  3. 静态资源必须加 Cache-Control + 版本号，否则浏览器缓存会导致"代码改了用户看不到"。
- **验证**：puppeteer 真实浏览器，国际象棋 boardDom=true / 64格 / 33棋子；围棋 SVG 存在 / 38线 / 370圆。截图确认棋盘完整。
- commit `4d65c7a` 已推 CNB。

## 公网引擎下拉只剩 4 个（ws 重连竞态，commit d293e23）

- **现象**：棋盘正常但引擎下拉只有 HTML 静态的 4 个（Stockfish/Reckless/BiaoZi×2），CCRL 引擎全没。
- **根因**：chess.js/go.js 的 `rpc()` 在 ws 未就绪时用 `ws.onopen = () => { wsReady = true; send(); }` **覆盖**了 connect() 的 onopen。页面加载早期 wss 首连若失败 → onclose 触发 setTimeout(connect,2000) 重连 → 重连后的 ws#2 的 onopen 只设 wsReady=true，**engines 请求永远没发**（注册在已废弃的 ws#1 上）→ loadEngines 的 promise 永远 pending → 下拉保持静态 4 个。
- **修复**：`sendQueue` 队列——ws 未就绪时请求入队，`ws.onopen` 统一 `sendQueue.splice(0).forEach(fn => fn())` 发送，重连不丢。chess.js + go.js 同样修复。
- **验证**：puppeteer 真实浏览器，下拉 = 12 个（BiaoZi×2 + Stockfish/Reckless + plentychess/alexandria/viridithas/quanticade/halogen/clover/berserk/ethereal），棋盘正常。
- **调试路径**：node ws 客户端连公网 wss 能拿到 12 引擎（服务端 OK）→ puppeteer 页面内手动 new WebSocket 能 OPEN（隧道 OK）→ 但 loadEngines 未生效 → 定位到 rpc 的 onopen 覆盖竞态。
- **教训**：ws 连接管理必须用「队列 + onopen flush」模式，绝不能用「覆盖 onopen」实现排队（重连必丢请求）。
